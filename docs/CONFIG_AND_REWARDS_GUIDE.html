CatClans Config and Rewards

A complete English operations guide for configuring CatClans without changing Java code. Paths are relative to plugins/CatClans/ after the first server start.

Safe Configuration Workflow

  1. Stop the server before changing storage, integration, or database settings.
  2. Keep config-version unchanged. It belongs to the migration system, not to your release label.
  3. Edit YAML with spaces, never tabs. Preserve indentation and quote MiniMessage strings containing special characters.
  4. Start the server and read the CatClans startup summary. Correct validation errors before allowing players to use the plugin.
  5. Use a staging server for reward, economy, permission, and storage changes. Test with a new clan and an existing clan.

CatClans keeps at most two managed configuration migration snapshots. These are recovery aids, not a replacement for server backups.

plugin.yml is packaged inside the JAR and defines Bukkit commands, dependencies and permission nodes. It is a build descriptor, not a generated server configuration file. Change it only in source code and rebuild the plugin.

Core Settings

Branding and feature flags

Replace {{SERVER_NAME}} in branding.server-name. Keep plugin-name: CatClans unless you are maintaining a deliberate fork. Each entry under features disables or enables one subsystem. Disabling a feature removes access to it; it does not erase saved data.

features:
  clan-core: { enabled: true }
  gui: { enabled: true }
  economy: { enabled: true }
  battlepass: { enabled: true }
  bank: { enabled: true }
  item-vault: { enabled: true }
  clan-wars: { enabled: true }
  rankings: { enabled: true }
  clan-homes: { enabled: true }

Clan creation and later edits use chat input. The player enters the requested value or cancel. No anvil input GUI is used.

clans.join.default-mode is INVITE_ONLY and invitations expire after 48 hours by default. security.prevent-owner-leaving: false allows the owner to leave and transfers ownership to the eligible member with the highest role priority; enable it to require an explicit transfer or clan deletion instead. advanced.service-worker-name changes only the background worker's diagnostic thread name.

Messages and GUI

messages.yml accepts MiniMessage, RGB colors, gradients and decoration tags. Clan tags may also use legacy RGB input such as &#D67DE9&l&oCAT. The visible character check ignores formatting codes. Small Caps conversion is applied by the plugin where configured.

Do not let players use click, hover, insertion, font, newline or other unsafe MiniMessage tags. Keep the plugin's input sanitizer enabled.

gui.yml contains every inventory view. Change materials using valid Bukkit material names, such as GOLD_BLOCK. Slots are zero-based: a 54-slot GUI accepts 0 through 53. Filler glass should have no name or lore and should retain hidden tooltips. The back arrow uses navigation history, so avoid replacing its configured action.

After visual edits, open every affected menu as a normal member, clan owner, outsider and administrator. Check titles, permissions, pagination, confirmation windows and chat-input return paths.

Ranks and Permissions

Default ranks are Owner 100, Co-Owner 80, Moderator 60, Member 40 and Recruit 20. Priorities range from 1 to 100; priority 0 may be shared, while non-zero priorities must be unique inside a clan. The owner always has all clan rights.

The rank pyramid allows members to manage only lower-priority members unless a specific override right has been granted. Role rights and individual member overrides are stored permanently.

Clan Bank and Economy

CatClans stores clan-bank balances but obtains player money through Vault. EzEconomy must be installed, registered as the active Vault Economy provider, and enabled in integrations.yml. currency.display-name is only the visible label.

general:
  enabled: true
  provider: "VAULT"
currency:
  display-name: "Coins"
clan-bank:
  enabled: true
  minimum-deposit: 0.01
  minimum-withdrawal: 0.01
  decimal-scale: 2
  rounding-mode: "HALF_UP"
  quick-amounts: ["100", "1000", "10000"]

There is no configured maximum bank balance. Quick amounts accept 1 to 7 positive values; players can also enter a custom amount through chat. Deposits remove money from the player only after all checks pass. Withdrawals require the clan right and sufficient bank funds. Keep deposit and withdrawal audit logging enabled.

Before enabling the bank

  1. Install Vault and EzEconomy.
  2. Start the server and verify that Vault reports EzEconomy as its provider.
  3. Set the visible currency name and decimal behavior.
  4. Test deposit, withdrawal, insufficient funds, invalid chat input and simultaneous access.
  5. Confirm the text log and the latest 18 GUI log entries.

Item Vault

The item vault is separate from the money bank. It starts with the pages available to the clan and can be expanded by Battlepass rewards up to absolute-max-pages: 7. Each page stores 45 item slots. Serialized items larger than 1,048,576 bytes are rejected.

Only one writable vault session is permitted per clan. Deposit, withdrawal and replacement actions can be logged. Keep the protections against shift-click, double-click, hotbar swaps and unsafe dragging unchanged unless the inventory transaction code is also reviewed.

Battlepass and Clan Rewards

Progress starts at level 0. Level 1 requires 100 XP, and every following level increases the requirement by 1.75 percent. There is no configured maximum level.

required XP for next level = base XP * 1.0175 ^ current level

How to create rewards

  1. Join the staging server with catclans.admin.battlepass.rewards or the matching administration bundle.
  2. Open /clan and enter the administration Battlepass reward editor.
  3. Select a level and configure one of the supported reward types in the level tree.
  4. Choose an amount that cannot exceed the matching absolute limit when combined with earlier rewards.
  5. Save, reopen the level, and verify the displayed item and amount.
  6. Level a test clan, then claim the reward as its owner. Rewards are clan unlocks, so ordinary members do not claim them individually.

Do not invent unsupported reward type names in YAML. The reward definitions are administered in game and persisted by the plugin; battlepass.yml controls the supported types and their presentation.

Clan Homes

Clans start with three home slots and can unlock more. absolute-max-slots must be at least the default count plus the largest possible Battlepass bonus. The default value is 103.

Safe destinations require solid ground, passable feet and head blocks, and no unsafe liquids or materials. The default deny list includes air variants, water, lava, powder snow, fire, cactus, magma blocks, campfires, sweet berry bushes, wither roses, End portals and gateways. Add dangerous custom-server blocks if another plugin introduces them.

Permanent Rankings

CategoryDefault points
Combat1 per valid kill against a non-allied member of another clan.
Members1 per current member.
Money1 per 10,000 bank currency.
Wars won10 per win.
Wars lost-5, multiplied by 0.5, resulting in -2.5 by default.
Activity1 per calendar day when at least one current member was online.

Total points combine the categories. Rankings may go below zero. Ties are resolved alphabetically by visible clan tag, with clan UUID as the final stable fallback. Cached positions update at most 60 seconds late by default.

Diplomacy and Clan Wars

Alliance requests expire after 24 hours and each clan may have up to 25 outgoing pending requests. Allowed war durations are 24, 48 and 72 hours. Both clans must confirm a war. Money wagers remain disabled by default.

An administrator can end a running war with /clanadmin war end <clan-one> <clan-two>. The plugin still calculates the result from stored deaths: the clan with more deaths loses. The command does not replace the recorded result with an arbitrary winner.

Storage, Backups and Text Logs

SQLite is the default and stores data in data/clans.db with WAL enabled. Use it for one Paper server. MySQL is prepared for external storage; set database.type: mysql only after creating the database and environment variables CATCLANS_DATABASE_USER and CATCLANS_DATABASE_PASSWORD.

Do not place database passwords in YAML. Stop the server before switching storage backends; changing the setting does not automatically migrate existing data.

Clan, vault and bank audits are written as daily text files under logs/clans, logs/vault and logs/bank. Default retention is 14 days. Keep console fallback enabled so failed log writes remain visible.

PlaceholderAPI

The identifier is catclans. Common values include %catclans_clan_name%, %catclans_clan_tag%, %catclans_clan_tag_formatted%, %catclans_rank%, %catclans_ranking_points%, %catclans_bank_balance%, %catclans_member_count%, %catclans_max_members%, %catclans_battlepass_level%, %catclans_battlepass_xp%, %catclans_battlepass_required_xp%, %catclans_ally% and %catclans_rival%.

Set empty fallbacks for players without clans to avoid literal placeholder text in scoreboards and chat. Placeholder reads use the memory cache and never query the database directly.

Performance Settings

The defaults use one serial database worker, a 2,048-operation queue, preload up to 5,000 clans, render GUIs only when opened, and disable live GUI refresh and periodic performance polling. This keeps Bukkit work predictable and avoids unnecessary tick tasks.

Change performance limits only after measuring with spark or equivalent tooling. Raising queues and caches can increase memory use; lowering them can reject work during bursts.

Final Production Checklist

  1. Replace all intended branding placeholders.
  2. Install Paper-compatible dependencies: Vault, EzEconomy, LuckPerms, PlaceholderAPI, and optionally InteractiveChat.
  3. Grant normal players catclans.default.*; grant staff bundles deliberately.
  4. Validate clan creation, chat-based editing, invites, confirmations, owner succession and deletion.
  5. Test bank, vault, home safety, role priorities, Battlepass reward claiming and ranking updates.
  6. Check database files, daily text logs and startup warnings.
  7. Create a full server backup before moving the build to production.
